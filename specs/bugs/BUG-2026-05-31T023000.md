# BUG-2026-05-31T023000: Variables Create transaction conflict (WriteConflict)

## Problem

When creating a variable for a site, two sequential database operations run inside separate MongoDB transactions:

1. `createDocument('variables', ...)` — creates the variable
2. `updateDocument('sites', siteId, ['live' => false])` — sets the site's live flag

Each operation opens its own MongoDB transaction. Under concurrent requests (multiple Swoole workers handling simultaneous variable creations for the same site), both transactions try to update the same parent document, causing a MongoDB WriteConflict (error code 112). The Mongo adapter's `withTransaction()` has no retry mechanism, so the conflict bubbles up as an unhandled `TransactionException`, producing a 500 error.

**Observed**: Browser shows "Failed to load resource: the server responded with a status of 500" on `POST /v1/sites/:siteId/variables`. Appwrite logs show `Transaction aborted` with stack trace `Mongo.php:3628 → Mongo.php:1627`.

## Root Cause Analysis

The `subQueryVariables` database filter (which populates the `vars` attribute when reading a site document) executes an additional `find('variables', ...)` query inside the transaction. This extends the transaction's duration — widening the window for concurrent writes to collide on the same site document.

Two code paths exhibit this:

- `Sites/Http/Variables/Create.php` — `updateDocument('sites', $site->getId(), ['live' => false])`
- `Functions/Http/Variables/Create.php` — `updateDocument('functions', $function->getId(), ['live' => false])`

Both are triggered by user requests (Swoole multi-worker architecture), and both inherit the `subQueryVariables` filter inside the MongoDB transaction, causing `find('variables', ...)` to execute within the transaction and extending its duration.

**Risk level**: Medium — it's a race condition that manifests under concurrent requests. Single sequential requests work fine.
