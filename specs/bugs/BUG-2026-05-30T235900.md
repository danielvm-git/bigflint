# BUG-2026-05-30T235900: GitHub VCS callback 403 due to eager email scope fetch

## Problem

When a user installs the Appwrite GitHub App and is redirected back to `/v1/vcs/github/callback`, the request ends with a 403 error instead of redirecting to the success URL.

**Actual behavior:** The callback handler throws/renders a 403 error page.  
**Expected behavior:** The installation is stored and the user is redirected to the configured success URL.  
**Reproduction:** Install the Appwrite GitHub App from the console Sites "create site / repositories" flow. GitHub redirects back with a valid `installation_id`, `code`, and `state`.

## Root Cause Analysis

The callback handler calls `OAuth2Github::getUserSlug($accessToken)` to determine whether the installation is personal (comparing the installing user's GitHub login against the installation owner). `getUserSlug()` delegates to `getUser()`, which **eagerly and unconditionally** fetches `GET /user/emails` from the GitHub API on every call — even though `getUserSlug` only needs the `login` field already returned by `GET /user`.

The OAuth token issued during a GitHub App authorization flow (`ghu_…`) does not carry the `user:email` scope unless the GitHub App is explicitly configured to request it. GitHub returns HTTP 403 on `/user/emails` for tokens lacking that scope. This surfaces as an unhandled exception / 403 response to the end user.

**Contributing factor:** The email-fetch logic was designed for the sign-in OAuth flow (where `user:email` is always requested). It was reused without adjustment for the VCS GitHub App flow, which operates with a narrower token scope.

**Risk level:** High — blocks the entire GitHub App installation flow for all new users.

## TDD Fix Plan

1. **RED**: Write a test that calls `getUserSlug($accessToken)` on a mock that returns a valid `/user` response but a 403 on `/user/emails`. Assert that `getUserSlug` succeeds and returns the `login` value without throwing.  
   **GREEN**: Lazy-load emails in `getUser()`: only call `/user/emails` the first time a caller actually needs `email` or `verified` (i.e., move the email fetch into `getUserEmail()` / `isEmailVerified()` directly, or guard it behind a check inside `getUser()` so the base `/user` payload is returned without email fields rather than erroring).  
   **verify**: `docker compose exec appwrite test tests/unit/ --filter=OAuth2GithubTest`

2. **RED**: Write a test that calls `getUserEmail($accessToken)` and `isEmailVerified($accessToken)` with a token that does have `user:email` scope. Assert that the email and verified flag are populated correctly.  
   **GREEN**: Ensure the refactored `getUser()` still fetches and merges email data when called through `getUserEmail` / `isEmailVerified`.  
   **verify**: `docker compose exec appwrite test tests/unit/ --filter=OAuth2GithubTest`

3. **RED**: Write an integration-style test (or mock-based) for `VCS/GitHub/Callback/Get` that simulates a GitHub App install with a non-email-scoped token and asserts the response is a redirect to the success URL, not a 403.  
   **GREEN**: No additional change needed once step 1 is fixed; this test validates the end-to-end behaviour.  
   **verify**: `docker compose exec appwrite test tests/e2e/Services/VCS`

**REFACTOR**: Remove the `$this->user` email mutation from the base `getUser()` and consolidate it into a separate `getEmailData()` helper called only from `getUserEmail()` and `isEmailVerified()`. This keeps the two data-fetching concerns separate and avoids 403s for callers that only need profile data.
